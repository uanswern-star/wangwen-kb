# 书库区说明

存放**从番茄等平台下载的原著全文**（采集原文），按「一本一书目」组织、按章节拆分。

## 定位：和 00-收件箱 有什么区别

| 区块 | 存什么 | 特点 |
|------|--------|------|
| `00-收件箱` | 还没整理的零散素材 | 临时、待分拣、会被搬走 |
| **`12-书库`** | **整本原著，按章节拆好的全文** | 长期留存、体量大、作为精读和拆解的底本 |
| `09-归档` | 不再活跃的条目 | 已完结/已用尽/已过期 |

简单说：**收件箱是过路站，书库是长期书房。**

书库里的正文是**别人的作品**，只作为学习和拆解用途，不混入 02-设定 / 04-剧情创意 等原创模块。
从书库提炼出的手法、梗、结构，**另建条目**放到对应模块，并在来源里标注出自哪本书哪一章。

## 日常入库：双击就跑

**双击桌面的「番茄入库」**，完事。不用记命令，不用管参数。

它自己做这些事：

1. 扫 `D:\Tools\books\` 里所有 TXT
2. **跳过已经入库的**（源文件没变过就跳过）
3. **跳过还在下载的**（旁边有 `.progress.json` 的）
4. 剩下的按章节拆好写进 `12-书库/`
5. 写报告、写日志，窗口停在结果页

跑完看两处：`_入库报告.md`（缺章 / 覆盖率）、`_入库日志.txt`（完整运行记录）。

## 目录结构

```text
12-书库/
├── _说明.md                  ← 本文件
├── _书籍ID清单.txt            ← 可选：只想导指定几本时用
├── _入库报告.md               ← 最近一次入库的完整性报告
├── _入库状态.json             ← 增量状态（已入库的书 + 源文件指纹）
├── _入库日志.txt              ← 每次运行的完整输出（追加）
└── 《书名》/
    ├── _book-info.md         ← 书籍信息卡（书名/作者/字数/ID/简介）
    ├── 0001-第一章标题.md
    ├── 0002-第二章标题.md
    └── …
```

章节数超过 200 章时，自动按每 100 章分卷：

```text
《书名》/
├── _book-info.md
├── 001-100/
│   ├── 0001-xxx.md
│   └── …
└── 101-200/
```

## 条目字段（章节文件）

沿用全库「双轨制」：YAML frontmatter + 正文。

```yaml
---
title: "章节标题"
book: "书名"
author: "作者"
chapter_num: 1
book_id: "番茄书籍ID"
status: 灵感
type: 采集-章节
updated: "2025-07-31 11:47"     # 章节更新时间，从正文里摘出来的
date: 2026-08-30
tags:
  - #采集
  - #采集/题材标签
  - #来源/番茄
source:
  - 番茄小说 - <book_id>
---
```

## 命令行用法（可选）

脚本都在 `D:\ProgramData\网文知识库\.workbuddy\tools\`：

| 文件 | 用途 |
|------|------|
| `入库.cmd` | 启动器（桌面快捷方式指向它） |
| `txt_to_kb.py` | 主脚本，**不带参数直接跑就是增量入库** |
| `txt_to_kb.py.v1.bak` / `.v2.bak` | 旧版本备份（出问题时可回退） |

```bash
PY="C:/Users/iflytek/.workbuddy/binaries/python/versions/3.13.12/python.exe"
SCRIPT="D:/ProgramData/网文知识库/.workbuddy/tools/txt_to_kb.py"

"$PY" "$SCRIPT"                # = 增量入库（等同双击桌面图标）
"$PY" "$SCRIPT" --dry-run      # 只看会动哪些书，不写文件
"$PY" "$SCRIPT" --force        # 忽略状态，全部重跑
```

其他参数：`--src` / `--dst` 换目录；`--vol-size`（默认 100）/ `--vol-threshold`（默认 200）调分卷；
`--batch <清单>` 只导指定书目；`--book-tag` 给 `#采集/<题材>` 打标签。

## 增量是怎么判断的

`_入库状态.json` 按 **书籍 ID** 记账，并记住源文件大小。判定顺序：

| 情况 | 动作 |
|---|---|
| 状态里有这本书，源文件大小没变 | 跳过 |
| 状态里有这本书，源文件变了（重下 / 补更） | 重新导入 |
| 状态里没有，但目标目录章节数已达平台值的 90% | 补登记，不重刷 |
| 状态里没有，目标目录也没有 | 当新书导入 |

所以**状态文件丢了也不会把整库重刷一遍**，最多慢一两秒。

## 注意事项

- 下载的 TXT 可能**缺章**（SVIP 章节、接口失败），导入后务必看 `_入库报告.md` 的覆盖率
- 平台侧可能出现**章节号重复但标题不同**（作者改稿 / 合章），脚本加 `-dupN` 后缀保留，不会静默覆盖
- 有的 TXT 会在正文后附**另一本书或续篇**（章节号从 1 重启），脚本会识别并保留，报告里会标重号
- 下载器有两种头部格式：`第N章 标题 / 章节更新时间 / 正文`，以及中间多一行纯编号的变体，脚本都会合并成同一章
- 章节标题里如果出现「第三回合」「第一节课」这类正文句子，脚本靠行长 + 章号回退判定剔除，不会切碎正文
- 布局变化（平铺 ↔ 分卷）时，旧结构的章节文件会移进 `_backup-<时间戳>/`，**不会直接删**
- 单本出错不影响其他书，失败原因会写进报告和日志
- 书库正文体量大，建议按需精读，不要整本丢给 AI 分析
- 用途限定：个人学习拆解，不对外传播、不商用
